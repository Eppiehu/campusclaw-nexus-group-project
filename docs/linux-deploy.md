# Linux 容器部署方案（待实现）

本文件是开发与老师验收时应遵循的部署设计。当前仓库没有 Dockerfile 或 Compose 文件，**尚不能运行**；请勿把此文档当作部署成功记录。

## 1. 目标拓扑

浏览器 → Web 网关（对外 `APP_PORT`，默认 8080）→ 前端静态资源 / Flask API → PostgreSQL、Redis、材料数据卷；Worker 从 Redis 消费索引、发卷、批改和周报任务。MCP 工具运行在受限服务或进程中，不直接对公网开放。数据库和 Redis 只在 Compose 内网可达。

| 服务 | 镜像来源 | 持久化 | 健康/就绪条件 |
| --- | --- | --- | --- |
| `web` | 固定版本 Nginx 与前端构建产物 | 无 | 首页与 API 代理正常 |
| `api` | 固定 Python 基础镜像 + 锁定依赖 | 材料卷只按需挂载 | `/health` 存活；`/ready` 检查数据库、Redis、迁移状态 |
| `worker` | 与 API 同一构建版本 | 材料卷 | 可连接数据库/Redis，队列消费正常 |
| `db` | 固定 PostgreSQL + pgvector 镜像摘要 | 独立数据库卷 | SQL 连接与扩展可用 |
| `redis` | 固定 Redis 镜像摘要 | 按任务持久化策略配置 | ping 成功 |

首个实现 PR 应提交多阶段 Dockerfile、Compose 文件、依赖锁定文件、`.dockerignore`、健康检查和镜像版本说明；本仓库当前只保留规划与无密钥配置模板。

## 2. 资源与网络

- 验收主机为 Linux x86_64；最低 CPU、内存和磁盘值需通过冷启动与压测实测后填写，未测前不得承诺具体容量。
- 只映射 Web 入口，数据库和 Redis 无宿主机公网端口；独立网络连接内部服务。
- 容器以非 root 用户运行，根文件系统尽量只读，材料目录单独授权；设置内存/CPU 限额、日志轮转和服务重启策略。
- 本地嵌入模型需在镜像构建阶段以固定版本和校验值准备，不应要求老师首次运行时临时从不可信来源下载；模型体积应纳入磁盘需求。
- Gunicorn 的进程/线程模型与 SSE 连接上限须通过压测确定，不能只按普通短请求估计并发容量。
- 演示环境允许本地 HTTP；公网交付需经 Nginx/可信证书配置 HTTPS，不能用自签证书冒充可信访问。

## 3. 冷启动顺序

1. 老师克隆指定提交，确认 Docker Engine、Compose 插件与磁盘空间；复制无密钥模板到私有配置，填数据库/JWT/演示账号密码。模型密钥如未提供，AI 接口须明确显示不可用。
2. 构建并启动 `db`、`redis`、`api`、`worker`、`web`；依赖服务通过健康检查后执行迁移。
3. 在 `demo` 环境显式执行幂等虚构种子数据初始化；记录生成的演示账号，不把密码写进公开日志。
4. 检查 `/health`、`/ready`、登录、本班材料查看、下载、问答、作业和后台任务；无模型密钥时将真实 AI 场景标为 NOT RUN。
5. 重启服务后确认数据卷与材料仍在；执行备份与恢复演练，核对材料版本和数据库一致。

## 4. 故障与回退

- 迁移失败不启动依赖新结构的 API/Worker，保留错误日志；数据库恢复需使用已验证备份，不直接删除卷。
- 新讲义索引失败继续使用旧活动版本；Worker 重启后恢复未完成任务或明确标记失败。
- 版本回退应同时检查数据库迁移兼容性、镜像版本、材料卷与索引版本；不允许只回退前端造成接口不匹配。
- 深度性能与安全测试只能在隔离演示环境运行，不在老师的其他服务或原网站上运行。
