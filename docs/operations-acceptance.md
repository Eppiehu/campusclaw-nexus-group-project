# Linux 部署与四项验收门槛

这四项是**最终交付要求**。当前仓库只提交规范，不包含运行代码；目前状态均为 **NOT RUN**。小组后续通过 PR 引入实现、脚本和实测记录后，才能逐项变更状态。

## 1. Linux 容器化部署

### 必须交付

- API、前端、Worker、PostgreSQL、Redis 的可复现镜像构建与 Docker Compose 编排；仅 Web 入口对外开放。
- 无真实密钥的环境变量示例、数据库迁移、虚构数据初始化、健康检查、持久化卷与备份恢复说明。
- 明确最低 Docker Engine/Compose 版本、CPU/内存/磁盘需求、启动端口和可配置项；默认端口约定为 8080，冲突时可通过环境变量修改。
- 容器以非 root 身份运行；镜像固定依赖版本，数据库和队列不绑定公网地址。首次启动失败时保留可读日志，不要求老师手工改源码。

### 验收

在一台干净的 Linux 主机上，仅按仓库文档配置必要的演示用环境变量，完成构建、启动、迁移、种子数据初始化；`/health` 返回 200，教师/学生可登录并完成本班材料查看、问答与作业主流程。重启容器后数据仍在；备份可恢复。记录发行版、架构、Docker/Compose 版本和完整操作步骤。公网 HTTPS 另列验收，不与容器冷启动混为一项。

## 2. 安全的自动化脚本测试

### 安全边界

- 脚本必须要求显式选择测试环境，默认拒绝生产域名、公网地址和非测试数据库；只操作标记为测试的虚构数据。
- 测试账号、令牌和模型密钥从测试环境变量读取，日志脱敏；脚本不得打印密码、JWT、API Key 或完整学生资料。
- 清理只针对本轮创建的测试资源，先验证资源归属，避免删除原有数据。压测与恶意输入测试不得对老师或其他人的生产环境运行。

### 必测场景

未登录访问；教师/学生角色边界；A/B 班列表、详情、正文、下载、检索、对话和 MCP 工具越权；JWT 过期、伪造与撤销；上传格式与大小限制；路径穿越；提示注入试图跨班取数；异步任务失败；敏感信息不出现在响应或日志。每项输出 PASS/FAIL/NOT RUN 和可定位的失败信息，CI 有 FAIL 时阻止合并。

## 3. 并发性能与容量结论

### 测试方法

- 在与目标部署相同规格的 Linux 环境，以 20、50、100、200 并发逐级运行；每级包含预热和固定时长测量，使用虚构数据。
- 分开测试普通业务 API、材料检索、SSE 对话、索引/批改后台任务；外部模型的延迟、限流和费用单独记录。
- 每级记录请求量、成功率、吞吐、p50/p95/p99、CPU、内存、数据库连接、Redis 队列长度、超时及错误类型；报告机器规格、镜像与配置版本。
- 同时运行跨班请求，确认负载下仍无越权和 SSE 串流；过载时应限流或排队并返回明确状态，而不是无界占用资源。

### 暂定通过线

在小组确定的验收机器上，普通只读 API **100 并发**时 p95 不高于 **2 秒**、服务端错误率低于 **1%**，且无权限串漏；SSE 对话至少 **20 并发**保持流事件归属正确，并记录首 token 与完整响应时间。是否达到 200 并发须据实报告，不能因 100 并发通过就写成“支持 200 并发”。若机器规格或模型限额使暂定线不适用，先在 OpenSpec 中说明并经小组评审，再修改验收线。

## 4. 可复现的虚构种子数据

- 至少包含 `teacher_a`、`student_a1`、`student_a2`、`student_b1`，A/B 两班及其成员关系；同班两名 A 班学生用于验证同纲不同卷。测试密码由初始化流程生成或从演示环境变量设置，不写进公开仓库。
- A/B 班各有可检索讲义，且内容足以识别跨班混入；A 班含材料版本、可命中问题、无证据问题、待审核知识缺口和回补材料。
- 包含可演示的 Agent 配置、提示词模板、一个可启停 Skill、一个 MCP 工具、作业模板、两名学生不同题目实例、提交、AI 初评、教师复核和周报草稿。
- 初始化可重复运行而不生成重复账号或资源；提供仅用于演示环境的重置方式。所有姓名、成绩、讲义和问答均为虚构数据，不引用真实学生资料。
- 验收时使用种子账号跑通教师与学生路径，并验证 A/B 班隔离；保留脱敏截图和接口记录。
